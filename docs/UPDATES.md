# GitHub 更新检查与升级提醒

[文档中心](README.md) · [返回首页](../README.md) · [安装与授权](INSTALL.md) · [部署/更新/卸载](DEPLOYMENT.md) · [故障排查](TROUBLESHOOTING.md)

## 1. 功能入口

点击左侧底部的 **“⇧ 更新”**，打开应用更新面板。

面板显示：

- 当前应用版本；由正在运行的程序自身提供，不在前端写死。
- GitHub 仓库配置。
- 是否启动时自动检查。
- 当前检查结果或失败原因。
- “保存设置”和“保存并检查更新”。

发现更高稳定版本时，GUI 顶部还会出现新版本横幅，提供：

- **查看发布页升级**：在默认浏览器打开该仓库对应的 GitHub Release。
- **忽略此版本**：当前版本不再自动弹出；出现更高版本时仍可提醒。
- **稍后提醒**：只关闭本次横幅，不持久忽略版本。

> 当前实现是“检查、提醒并打开发布页”，**不会在后台自动下载、替换、安装或重启应用**。下载新产物后，按 [INSTALL.md](INSTALL.md) 和 [DEPLOYMENT.md](DEPLOYMENT.md) 完成核验与更新。

已经安装旧版本、需要替换程序时，按 [DEPLOYMENT.md · 已有安装如何更新到新版本](DEPLOYMENT.md#已有安装如何更新到新版本) 操作。若发布页没有安装附件（例如仅源码发布的 `0.1.1`），说明该版本不提供新安装包，保持当前安装即可。

## 2. GitHub 仓库

应用已内置公开仓库：

```text
zhumengkang/claude-session-manager
```

打开“更新”面板会直接显示该地址，无需手动填写。使用 fork 或自建构建时，可以改成自己的 `owner/repository`；只接受 `owner/repository`，不要粘贴 URL、令牌、Cookie 或其他凭据。把输入清空并保存时会回退到内置仓库，不会关闭更新检查。

## 3. 自动与手动检查

- 已内置仓库且开启自动检查后，应用启动时发起一次检查。
- 应用持续运行时，每 6 小时再检查一次；窗口处于隐藏状态时跳过周期检查。
- 点击“保存并检查更新”可以随时手动检查。
- 同一仓库的并发点击共用一个进行中的请求。
- 切换并保存新仓库后，旧仓库的迟到响应不会覆盖新面板。
- 后台失败不会弹出全局错误 toast，也不会影响会话浏览和恢复；打开更新面板可查看状态并手动重试。
- 手动检查失败会在更新面板和 toast 中显示原因。

## 4. GitHub Release 要求

更新检查读取 GitHub 官方接口：

```text
https://api.github.com/repos/<owner>/<repository>/releases/latest
```

要产生稳定升级提醒，仓库需要：

1. 是无需凭据即可读取的公开仓库。
2. 已有 GitHub 的“latest”稳定 Release。
3. Release 不是草稿或预发布。
4. 标签使用语义化版本，例如：

   ```text
   v0.2.0
   0.2.0
   ```

5. 最新版本高于当前运行版本。

同版本或更旧版本不会弹出升级横幅。非语义化标签（例如只有日期或 `stable`）会返回明确错误，不会被猜测成新版本。私有仓库、凭据登录和自定义 GitHub Enterprise 基址当前未实现。

## 5. 忽略版本与重新查看

“忽略此版本”保存的是规范化版本号，而不是永久关闭更新：

- 后台检查到同一版本时不重复弹出横幅。
- 手动检查仍可在面板中查看该版本，并重新打开发布页。
- 更高版本出现后仍会提醒。
- 更换仓库会清除旧仓库的忽略记录。
- 关闭自动检查不会删除仓库或忽略记录。

## 6. 设置保存位置

| 平台 | 更新设置文件 |
| --- | --- |
| macOS | `~/Library/Application Support/com.claude.sessionmanager/update-settings.json` |
| Windows | `%APPDATA%\com.claude.sessionmanager\update-settings.json` |

文件只保存仓库名、自动检查开关和忽略版本，不保存 GitHub 凭据或会话正文。损坏或无法解析的设置会返回错误，不会被静默覆盖。

## 7. 网络与安全边界

- 后端固定访问 GitHub 官方 API 和 `github.com` 发布页，不接受自定义 API 基址。
- 请求带超时和响应大小上限，避免更新检查长期阻塞或读入异常大响应。
- 网络请求在非阻塞任务中执行，不使用 macOS Terminal 的同步主线程恢复路径。
- 发布页必须属于当前配置的仓库，并位于 `https://github.com/<owner>/<repository>/releases/tag/` 下。
- Release 名称和版本在 GUI 中以纯文本显示，不作为 HTML 执行。
- 不上传会话、收藏、项目路径、Token 或本机身份信息。
- GitHub 会按自己的服务策略看到常规 HTTPS 请求和源 IP；匿名公开 API 也可能限流。

“打开发布页”不等于已验证新安装包。仍应核对来源、版本、架构、签名状态和安装说明，再决定是否安装。

## 8. 常见问题

| 状态 | 原因与处理 |
| --- | --- |
| 未找到公开仓库或稳定 Release | 确认内置仓库可公开访问，且已有非草稿、非预发布 Release；如改用 fork，检查 `owner/repository` 是否拼写正确 |
| GitHub 限流或拒绝 | 稍后重试；不要在配置中加入 Token 或凭据 |
| 标签不是语义化版本 | 将发布标签改为 `v1.2.3` / `1.2.3` 形式后重新发布 |
| 网络超时 | 检查网络后手动重试；后台失败不影响会话功能 |
| 已是最新版本 | 当前运行版本大于或等于最新稳定 Release |
| 忽略后仍想查看 | 打开“更新”并手动检查 |
| 想一键自动安装 | 当前未实现；需要另行设计签名更新包、下载校验、平台安装与回滚流程 |

## 9. 当前验证边界

普通 Rust 测试覆盖仓库校验、语义化版本比较、忽略版本、草稿/预发布和外部地址拒绝、设置持久化及损坏文件保护。前端 mock 冒烟覆盖更新面板、版本横幅、纯文本渲染、忽略/重新查看、后台失败静默和发布页 IPC。

这些测试不依赖真实 GitHub 仓库，因此不能单独证明某个未来仓库的 Release 配置正确。当前公开仓库 latest stable 为 `v0.1.1`（源码版，无安装附件）。2026-11-26 已在 Windows 和 macOS 安装版 0.1.0 中用内置仓库完成一次真实只读检查；当时 latest 为 `v0.1.0`，面板显示同版本。发布 `v0.1.1` 后，0.1.0 安装版再次检查会显示升级横幅，可用于验证更高版本提醒。该检查只读取公开 Release，不下载或安装任何附件。
